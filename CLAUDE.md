# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Sidereus** — a web app that tells a beginner amateur astronomer whether tonight is worth setting up for (go / marginal / no-go) and which Messier and Caldwell objects to point at, with an eyepiece pair from their own kit. Product requirements, invariants and tunable scoring parameters live in `@context/foundation/prd.md`; the stack rationale in `@context/foundation/tech-stack.md`. Work runs through the 10x `context/` workflow with in-flight changes under `context/changes/<id>/`. **Starting a session: read `context/handoff.md` first** (current state, priorities, next step); the roadmap is `context/foundation/roadmap.md`.

Product code so far: the pure sky engine in `src/lib/engine/` and the generated Messier and Caldwell catalogues in `src/lib/catalogue/` (roadmap F-01, S-03), plus per-user observing sites, telescopes and eyepieces managed under `/gear` (S-01), and the gated `/tonight` dashboard (S-02, S-11): the verdict and dark window over tiles that open focused pages, with every object that cleared the bar ranked on `/tonight/targets` by the engine's pure scoring (`score.ts`, `ranking.ts`, `eyepieces.ts`, `verdict.ts`), with the Open-Meteo forecast behind a Workers KV cache in `src/lib/forecast/` (only `kv-cache.ts` imports `cloudflare:workers`; tests pass an in-memory cache). Tonight also shows the next seven nights at the selected site (S-05): `sevenNightOutlook` in the engine gives nights 1-3 a verdict and nights 4-7 only a cloud outlook, rendered by `NightStrip.astro` on `/tonight/nights` (since tonight-dashboard, `/tonight` is a dashboard of tiles opening focused pages for the targets, the Session plan, the Moon, the planets and the nights). The Session plan (S-05, session-plan-timeline) is `TonightView.sessionPlan`, built only with the `withSessionPlan` option of `loadTonightFor` (the dashboard and `/tonight/plan` pass it): the night from sunset to sunrise on one axis, drawn by `SessionTimeline.astro` on `/tonight/plan` as the night's lines (sunset, dark window, Moon, sunrise, one per line), a legend, and one row per recommended target by best time: "Best 22:40 · window 21:40–23:10 · SW, 45°" above a static server SVG altitude curve (each row carries its `track` of altitudes over the axis and `peakAltitudeDeg`, the plan `minAltitudeDeg` and `trackStep`; the geometry is the pure `src/lib/tonight/altitude-curve.ts`, horizon to zenith on one scale), with the dark window shaded, the minimum altitude dashed, the best window thicker and a dot at best (the dashboard's tile shows only the next target). Tonight shows a Site card and a Telescope card (S-05 / S-08, ui-user-adjustments, `GearCard.astro`), each with a select once the user owns two or more: `?site=<id>` and `?telescope=<id>` on the page shell are remembered in the `sidereus-site` / `sidereus-telescope` cookies and reach the `TonightContent` server island as props (ids only, never coordinates), which resolves them against the user's own sites and telescopes (`src/lib/tonight/gear-choice.ts`, falling back to the oldest). The verdict check (M-2 S-07, `src/lib/sky-checks/`) stores the sky headline each signed-in Tonight view shows in the per-user `sky_checks` table: `TonightContent` calls the `record_sky_verdict` RPC through its shared `defer` (the Worker's `waitUntil`), fire and forget, the one database write from a GET in the app; the RPC is idempotent per (user, site, night) and decides with the database clock, overwriting only before the dark window starts and never after an answer. Tonight's `SkyCheckCard` asks about the newest open night of the last two, and `/log/sky` lists every night whose dark window has started with the tally (`claim.ts` holds the match rule); both post plain Astro forms to `POST /api/log/sky/[id]`.

Observing progress (M-3 S-05, observing-progress): `src/lib/progress/` holds `observingProgress(entries)`, one pure rule from log entries to the Messier and Caldwell checklists (110 / 61, catalogue order) and the planets' and Moon's first nights, over `seenSummaries` (entries rated 3 or above, each night once), so progress and the ranking's seen tag cannot drift; its input is `observationStore.listSeenEntries`, which pages the read past PostgREST's 1000-row cap (`night desc, target asc, id asc`; the first page asks for an exact count, later pages advance by the rows received and stop at it, so any `max_rows` reads it all in one request normally), the one seen read for Tonight and the page alike. Tonight marks every target never seen (`notSeenYet`) with `NotSeenMark.astro`: a tooltip button inside a card's `<h3>` (`NotSeenTip`, one `data-open` state driven by `not-seen-tip.ts`) or, where a button is not allowed (the tile's link, a row's `<summary>`), a static icon explained by `NotSeenLegend`. `/log/progress` (`ChecklistGrid`, `SeenList`, linked from `/log`'s header) is network-only like `/log`.

Observing milestones (M-3 S-06, observing-milestones): `src/lib/progress/milestones.ts` derives the 11 `MILESTONES` from `observingProgress` (first Moon, first planet, all planets, first galaxy, globular and nebula, 10 / 25 / 50 / 110 Messier, all Caldwell), each with the night it was reached, and `withStored` lays the stored record over that derivation, so a milestone outlives the entry that reached it. The `observing_milestones` table keeps each milestone once per user (unique `(user_id, key)`); `milestoneStore.record` (`src/lib/observations/milestone-store.ts`) inserts ignoring duplicates and returns the keys it actually stored, so two saves at once cannot both celebrate. RLS lets a user write their own rows directly, accepted by the owner (a forged row fools only its author) and pinned in `tests/db/milestones.test.ts`; a new milestone needs a new migration widening the key check (the test keeps SQL and TypeScript in step). `reachedBySave` in `src/lib/observations/celebrate.ts` runs the order inside each save route: a counting save (a create or an edit rated 3 or above) reads `before`, writes, reads `after`, records `reached(before)` ∪ `reached(after)` in one insert and celebrates `newlyReached` ∩ inserted; an edit to 1-2 or a delete reads and records `before` first, then writes, and never celebrates; a create rated 1-2 does nothing. A failed milestone read or record never blocks the write: `logMilestoneFailure` is the one allowlisted log (a fixed step word plus error and cause names, never a message). The redirect carries the reached keys as repeated `milestone` params (`withMilestones`, fixed `MILESTONES` keys, never a value; `milestone` is in the service worker's `NOTICE_PARAMS` (`src/lib/offline/copies.ts`), so a Tonight page that carries it is never stored). `GearShell` renders `MilestoneCelebration.astro` for a signed-in user whose URL has valid keys (`readMilestoneParam`): a native modal `<dialog data-milestone-celebration>` on a night-sky card (Award, plural label, the names, Continue, "See your progress"; no timer, no date, Esc closes; on close focus goes to `<main>` via `focusMain` from `toasts.ts`, and a save toast's timer waits for it, `celebrationHolding`), which its script opens with `showModal()` and, as it opens, removes the `milestone` params with `history.replaceState` (`withoutParams` from `src/lib/toasts.ts`), so a reload never replays it; the save's own toast shows beside it, and e2e finds the dialog by its attribute, never the toast region. The Milestones band on `/log/progress` (`MilestoneList`) lists all 11, reached (night) or ahead (progress), and is the same rule's persistent view.

Sky events (M-3 S-07, sky-events): `skyEvents(site, fromNight, nights, darkThresholdDeg)` (`src/lib/engine/events.ts`, pure; `EVENT_WINDOW_NIGHTS` = 30 nights from the selected one) returns the window's events in moment order: eclipses, greatest elongations and oppositions (searched in `events.ts`), close Moon-planet and planet-planet pairings within 5° computed from the site (`pairings.ts`) and meteor-shower peaks (`meteors.ts`, found by `Search` over the Sun's J2000 longitude, never the of-date `SearchSunLongitude`). **A solar eclipse stays until its partial phase ends** (owner decision A, 2026-10-14): `skyEvents` also returns the previous observing night's solar eclipses whose partial phase ends after the window's start minus 12 h (so the morning eclipse of day D is still returned for the night of D after dawn, with its own earlier `night`), and stays free of the clock. **Visibility and the invariant:** every event carries `visibility`, decided in one place (`visibleAt`: at or above 10° at a sampled moment of the night's dark window, or its twilight span flagged `shortNight`, with the Sun at or below −6°; `eclipseVisibility`: from 2°, "low, needs an open horizon" under 10°; `best` is the peak when the peak is up, else, for a `partly` visible eclipse, the moment the body clears 2° while the phase is still in progress, bisected between the peak and the highest contact, never the contact itself), and only visible events are ever worded as something to go out for (PRD invariant, US-07): the tile, the verdict line and every "best time" read `isNotableEvent` (visible, not a penumbral lunar eclipse). A shower peak is a night, never a minute: the radiant is judged on the peak night, else the night before or after (`bestNight`), and the shower counts for `tonight` and `next` on that best night (`goNight`; the page still groups its row by the peak night, and `meteorEvents` keeps a peak from the two days before the window when its best night is the window's first). The shower table, `src/lib/catalogue/meteor-showers.ts` (keys typed by `SHOWER_KEYS` / `ShowerKey`, which also type `tonight.events.showerName` and `showerNameInLine` in both languages; the bright-Moon note shows on a visible shower only), is eight showers entered by hand as rounded facts (peak night and rate from NASA's pages, radiant and speed from the IAU MDC, each cross-checked; nothing from the IMO, whose list needs written permission; peak longitudes derived by our engine, not copied); its licence note is `LICENSE-DATA.md` ("Meteor showers", not legal advice) and `Attribution.astro` credits both. A solar eclipse row, visible or not, always carries the fixed eye-safety line (`tonight.events.solarSafety`); the tile and the verdict line say "eclipse glasses only". `TonightView.skyEvents` exists only with the `withSkyEvents` option of `buildTonight` / `loadTonightFor` (a failure logs a fixed line with the error's name and drops only that block): `formatSkyEvents` (`src/lib/tonight/sky-events.ts`, which takes the request's `now`; `buildTonight` passes the real one, and the next night's sunset for `night: "next"`) words the events into `events`, `tonight` (notable visible events whose go night is the selected one, solar eclipses first, then by moment, so "eclipse glasses only" never hides behind "+N more") and `next` (the earliest from it on, a solar eclipse winning a tie). A solar eclipse whose partial phase ended before `now` is dropped from all three; one still to come counts in `tonight` (and as `next`) when its local date, in the site's zone, is today or its night is the selected one, and its day is worded from today's date, not from the observing night: `dayWord` (`today` or `tomorrow`) and `at` (the best time, the peak when that is visible), "Today, 11:22" / "Tomorrow, 11:22" (Polish "Dziś, 11:22" / "Jutro, 11:22"), and "Today, 17:04" for an afternoon eclipse on its own day instead of "Tonight" (the tile writes them lowercase between its separators, "· tomorrow, 11:22 ·", like "tonight"); a later day reads its day and time. `/tonight/events` (`EventsPageContent`, `SkyEventList`) lists the whole window by night and is the seventh entry of `TONIGHT_PAGES`. On the dashboard `EventsTile` is the second tile, always shown: `next` ("Perseids peak · night of 12/13 Aug", `eventsTileLine`) or "Nothing to go out for in the next 30 nights". On an event night `VerdictCard`'s `event` prop adds one muted plain-text line under the reason, "Tonight: <name>" plus "+1 more" (`eventsVerdictLine`, `data-verdict-event`, no link; a solar eclipse reads "Today, 11:22: …" or "Tomorrow, 11:22: …" from `dayWord` and `at`, and every other event uses its in-sentence `verdictName`, Polish lowercase after the colon: "Dziś: maksimum Orionidów", "Dziś: opozycja Marsa", "Dziś, 11:22: częściowe zaćmienie Słońca, tylko przez okulary do zaćmień"; the Polish titles carry no colon ("Opozycja Marsa", "Największa elongacja Merkurego"), per-key records `elongationName` / `oppositionName` and their `…InLine` forms, never a grammar function; owner, 2026-10-14): no room is reserved (the owner accepts the one-line shift, plan review F3), `VERDICT_MIN_HEIGHT_CLASS` and the skeleton keep today's height, and `tonight-phone.spec.ts` hides the line (`[data-verdict-event]{display:none}`) while it measures the cards. The kind icons and the visible / not-visible mark icons (`CircleCheck` / `CircleSlash`) come from the shared map in `fact-icons.ts`, and each detail, the visibility sentence, the notes and the safety line are one `Fact` each. `/design` pins the line, the tile and a `SkyEventList` window (30 nights from 2027-07-25 at Warsaw, with the 2027-08-02 solar eclipse) from fixed data (`src/components/design/event-samples.ts`).

Finder chart (M-3 S-03, finder-chart): `/tonight/finder?object=M31&from=targets|planets|plan` (plus the usual `?site=`, `?telescope=`, `?night=`; `finder.astro` shell + `FinderContent` server island, components in `src/components/finder/`) is the first full-plan page, opened by the "Finder chart" quiet link on every `ObjectDetails` and `PlanetCard` (never the Moon's) for every account. The plan is checked twice: the shell calls `requireFullPlan` (a free or signed-out visitor gets `FinderLocked`, the explainer with the fixed precomputed `EXAMPLE_FINDER_CHART`, and no island), and the island's loader `loadFinderFor` (`src/lib/finder/load.ts`) calls it again before it reads Tonight or the star file, because `/_server-islands/*` is not behind the middleware and an island URL replays without the session; `scripts/smoke.mjs` proves both layers over HTTP (test-plan 6.4). The page never redirects: every state (`chart`, `locked`, `not-ranked`, `no-gear`, `failed`) is a 200 marked `data-finder-state`, and only the chart state's root carries `data-finder-chart` (never inside `FinderChart`, which the free example renders too). The chart is a static server-rendered SVG, two panels (overview from the start star to the target with the numbered hop, and the finder's 7° field with the finder circle, reflex rings and the finding eyepiece's circle) built by the pure engine `finderChart` (`src/lib/engine/finder.ts`; stars come in as an argument) from the deeper star file (`loadFinderStars()`, 25,791 stars to magnitude 7.5, server-only, a dynamic `import()`; no star data reaches the browser and `build-sw.mjs` fails the build if `finder-stars` lands in `dist/client`); geometry in `src/lib/finder/chart-svg.ts`, the sentences in `steps.ts`. The start star is the nearest one above the site's minimum altitude and no fainter than `startStarMaxMagForBortle` (4.5 / 3.5 / 2.5, never above the naked-eye limit); the hop is the exact layered search of `parameters.ts`'s `HOP_*` candidates. **Overhead rule:** when either panel's centre is at or above `FINDER_OVERHEAD_ALT_DEG` (80°) or the zenith falls inside a panel, both panels switch to the pole as "up" (`data-finder-orientation="overhead"`, a zenith cross in a panel that holds the zenith or an arrow on the panel's edge pointing toward it (`zenithEdge`, owner decision 2026-10-13), "Nearly overhead" instead of a compass point); otherwise `facing`, "up" being the vertical through each panel's centre. Failures are logged by two allowlisted fixed lines (`error.name` only) and render `failed`. **Offline storage and the plan-loss drop** (O-4, D-13 to D-15): a chart opened online by a full-plan user is stored as a pair like the Tonight pages, keyed by `(siteId, page, target, kind)` (`storedPageOf`, `copyMetaFor` and `dropFinderCopies` in `src/lib/offline/copies.ts`; no next-night copy, no prefetch, listed on `/offline`); every Tonight island's `OfflineCopy` (and the locked finder root) carries `data-plan="full|free|unknown"` and `data-plan-at` (when the plan was read, server clock) from `accountPlanForCopy`, and the worker drops every stored chart only on an explicit `free` (a failed plan read is `unknown`, logged with its code: it neither stores nor drops charts), at the first online Tonight or finder answer after the plan is lost; `freeSince` (the newest free answer's plan-read time, never the device clock) refuses a chart whose plan was read before it. Charts expire 36 h after the site's last refresh and go with sign-out like the other copies.

What to expect (M-3 S-04, what-to-expect): each ranked deep-sky target on `/tonight/targets` and its finder chart says in one sentence what it will look like in the user's own telescope from their site. The rule is the pure `expectationFor(object, bortle, apertureMm)` in `src/lib/engine/expectation.ts`, one of 22 `ExpectationKey`s (`EXPECTATION_KEYS`; no Moon input, the line is a property of object, site and telescope): a contrast deficit (the core surface brightness from `effectiveSurfaceBrightness` minus the moonless zenith sky for the Bortle class, less an aperture term of 0.5 mag per doubling from 150 mm) falls into four bands (`bright`, `smudge`, `faint`, `limit`; `contrastBand`, after a near-limit floor that makes an object within 1 mag of `telescopeLimitingMag` at least `faint`), and a per-type table turns the band into the key (galaxies, nebulae, planetaries, globulars by aperture and headroom, open clusters by size, with fixed keys for M24, M40 and M73). Its numbers are the `EXPECT_*` candidates after `WASHED_OUT_TYPES` in `parameters.ts`. `src/lib/engine/fixtures/expect-reference.ts` (test-only, not in `fixtures/index.ts`) is the source-cited reference: showcase entries and hard cases (M42 under Bortle 7, M56 at 200 mm, the Helix and the Owl, NGC 7000, a faint galaxy near 11 mag, M33 at Bortle 9), each with at least two published sources, and `KNOWN_DIVERGENCES` for the entries the rule still gets wrong (NGC 7000 and NGC 4889); a failing reference is an engine finding, never a fixture edit. The phrases are `tonight.expect.phrase[key]` in `en.ts` / `pl.ts` (plus `locked` and `lockedFinderLine`). The server helper `src/lib/tonight/expectation.ts` (`expectationKeyFor`, `expectationText`, `expectationView`) is the gate: a confirmed full plan (`getAccountPlan`, which fails closed) gets the lines, an explicit `free` read gets one muted locked line under the Targets count, and a failed read (`unknown`, from `accountPlanForCopy`) gets neither, so a paying user is never told they lack the plan because of a transient error. The key is computed only in the Targets island (`TargetsPageContent`, passed down through `ObjectCard` / `ObjectRow` to `ObjectDetails`) and in `loadFinderFor`'s `chart` state (`expectation`, after the plan guard; a planet's chart shows its existing free `note` from `view.solarSystem`), never in `TonightView` or `loadTonightFor`, so a free account's island HTML never holds a phrase and a leaked island URL renders nothing signed out. Markers: `<div data-expect="<key>">` (a `Fact` root; a planet's own key on its chart) and `<p data-expect-locked>`; matching the valued `data-expect="` matters because the bare attribute is a substring of the locked one. `scripts/smoke.mjs` proves the gate over HTTP (`expect 1` free, `expect 2` full, `finder 3`, `expect 3` signed out, from the Targets island URL captured off its shell) and `tests/e2e/what-to-expect.spec.ts` in the browser. **Offline** (owner decision O-2): a stored Targets copy keeps its lines until the next online visit replaces it, its next-night copy is refreshed, or it expires 36 h after the site's last refresh; there is no plan-loss drop for Targets pages (only finder charts have one), since the text derives from public catalogue data and the user's own gear.

Adjustable session plan (M-3 S-08, adjustable-session-plan): a full-plan user edits tonight's Session plan on `/tonight/plan` (move up or down, remove, add, one Save), and the list is stored in `public.session_plans`, one row per user, site and night (`targets text[]`, the whole ordered list; unique `(user_id, site_id, night)`; RLS with the four `_own` policies, insert and update also check that the site is the owner's, as `sky_checks` does; `on delete cascade` from the site; checks on count, shape and the catalogue's key pattern; `tests/db/tables.ts` takes it through the `needsSite` option and `tests/db/session-plans.test.ts` pins the rest). The guardrail is that a row exists only when the engine's own rule gave the key a window tonight: the pure `applyPlanEdits` (`src/lib/tonight/plan-edits.ts`) builds the rows only from the suggested plan or from `rankObjects`' `reachable` list (every catalogue object the telescope can reach, each with its best window, including below-bar and washed-out ones; the saved list itself never makes a row), and a saved key with no window tonight goes to `notTonight` (muted "Not on tonight's plan", kept until removed). `src/lib/tonight/plan-window.ts` (`deepSkyWindow`, `solarSystemWindow`, `planetWindowFor`) is the window rule of the build's planet window (`planetWindowFor`) and the save route's check of newly added keys (`keysWithoutWindow` in `src/lib/session-plans/checks.ts`); `solarSystemWindow` is held to the build's planet and Moon rule by the parity test `plan-window.test.ts`, not by shared code; a key already on the stored list is never re-checked (F4), so a list stays saved after the site's minimum altitude rises. `loadTonight` computes the night date once (`tonightDateForSite`, plus one day for `night: "next"`) and passes it to `readPlanEdits` and to `buildTonight`; edits and the editor exist for tonight only (D9), and both routes compare the posted night with `tonightDateForSite(site, now)` (`errors.sessionPlan.nightOver`). **Gates:** both routes call `requireFullPlan` before any read or write; `readPlanEditsFor` (`src/lib/session-plans/read.ts`) checks the plan itself (`getAccountPlan(locals) === "full"`, else `null` with no query), because `/_server-islands/*` is not behind the middleware; `/api/tonight` is in `PROTECTED_ROUTES`, so a signed-out POST goes to sign-in. **Island states:** `PlanPageContent.astro` marks the plan area `data-session-plan-state` with one of `edited`, `suggested`, `locked` (free account: one muted `PlanNote` line), `held` (D5: a list is saved but the night does not pass, so the edits are held, not applied; the "Edited by you" line with Reset shows, no editor) or `unavailable` (D14: the account-plan read is `unknown`, the saved-list read failed, or the view has no session plan), plus the boolean markers `data-session-plan-edited`, `-held` and `-locked` that `scripts/smoke.mjs` greps. In `unavailable` the island shows the suggested plan and one muted line; when the plan read is `unknown` or the saved-list read failed (a view with no session plan is also `unavailable` and keeps its `OfflineCopy`) it renders no `OfflineCopy`, so the worker commits nothing and the earlier stored copy survives, and a failed saved-list read logs one fixed line (`tonight: plan edits read failed` plus the cause's code or name, in `load.ts`, allowlisted in `ALLOWED_DISABLES`) and keeps D14; the dashboard tile keeps its `OfflineCopy` (the dashboard is unaffected). When the plan is lost (D11, OQ23) the edits stay in the database and return with the plan, the island shows the suggested plan, and a stored edited copy is replaced at that page's next online answer (no plan-loss drop in the worker). **Routes:** `POST /api/tonight/plan` (`src/pages/api/tonight/plan.ts`: database, plan, shape via `savePlanSchema`, catalogue via `isKnownTarget`, own site, tonight's date, windows of the keys the list adds, then `sessionPlanStore.save`) and `POST /api/tonight/plan/reset` (deletes the row); every refusal redirects to `/tonight/plan?error=<fixed message key>` (plus `site=` only when it passes `isGearId`) and success to `?saved=plan` or `?saved=plan-reset` (`src/lib/session-plans/redirect.ts`); no submitted key, night or coordinate ever reaches a URL or a log. **Offline:** `saved` is in `NOTICE_PARAMS` (`src/lib/offline/copies.ts`), so the toast URL is never stored, and after a save the page posts the clean URL to the worker as `{ type: "store-page", url }` (`storePageMessage` in `page-state.ts`, validated by `storeRequestFrom`: same origin, `/tonight/plan` only, only a well-formed `site` param); `storePageNow` in `src/sw.ts` fetches the shell and island and commits them through the usual rules, so the stored copy shows the edits at once (D7 b); runs are coalesced per page (`createCoalescer`, `src/lib/offline/coalesce.ts`): a request during a run re-runs once after it, never dropped; the after-save landing (`/tonight/plan` with `saved=plan|plan-reset`) does not race the worker's network timeout (`awaitsNetwork` in `copies.ts`, the `waitForNetwork` argument of `networkFirst`): the stored copy answers only if the fetch fails; there is no offline editing, and `?night=next` copies never carry edits. **UI:** an added deep-sky row that is below the bar (on no Targets list) links to its finder chart, `/tonight/finder?object=<id>&site=&telescope=&from=plan` (`FinderFrom` gained `plan`, F9), while a cleared or washed-out one keeps `/tonight/targets#object-<id>` (Targets cards and rows carry the anchors); `PlanEditor.tsx` is the editor island (`quiet` `icon` buttons for Move up, Move down and Remove, an "Add a target" picker, one Save (disabled until the list changes) or Cancel, `data-plan-editor` open or closed; the dashboard's Session plan tile follows the edited plan (D13) through the same `readPlanEditsFor` hook. `scripts/smoke.mjs` proves the gate over HTTP (`plan 1` to `plan 11`: free refusal, suggested plan, full save, demotion, edits back after re-grant then reset, signed-out save, replayed island URL, then refusals for a never-visible M7, a foreign site, an unknown NGC1 and a duplicate key, and the island still suggested) and `tests/e2e/session-plan-edit.spec.ts` and `session-plan-store.spec.ts` (also reset and a slow, delayed redirect after save) the browser (specs skip through `planEditable(page)` only on `held`; any other non-editable state fails).

## Tripwires (read first)

- **Never write to `context/archive/`.** Archived changes are immutable; open a new change instead.
- **Run `nvm use` before any npm/npx/node command.** `.npmrc` sets `engine-strict=true` and `package.json` requires Node ≥ 24.16, so npm refuses to install or run under the shell's default Node 24.13. `.nvmrc` pins 24.21.0. In a non-persistent shell prefix every command with `export NVM_DIR="$HOME/.nvm" && . "$NVM_DIR/nvm.sh" && nvm use >/dev/null &&`.
- **Never edit `src/lib/catalogue/messier.json`, `messier.meta.json`, `caldwell.json` or `caldwell.meta.json` by hand.** They are generated together by `npm run catalogue:build` from a pinned OpenNGC commit and covered by `.prettierignore`; `messier.test.ts` and `caldwell.test.ts` assert their shape and provenance. Change the generator, re-run it, review the diff.
- **Never edit `src/lib/catalogue/bright-stars.json` or `bright-stars.meta.json` by hand.** They are generated by `npm run stars:build` from a pinned HYG v4.1 commit (CC BY-SA 4.0) and covered by `.prettierignore`; `stars.test.ts` asserts their shape and provenance. Islands import them only through `stars.ts`, which must never import `./index` (that would ship `messier.json` to the browser). Polish names live in `star-names.ts`. Change the generator, re-run it, review the diff.
- **Never edit `src/lib/catalogue/finder-stars.json` or `finder-stars.meta.json` by hand.** `npm run stars:build` writes them in the same run as the bright-star pair, from the same pinned HYG v4.1 commit (CC BY-SA 4.0 on top of ESA's Hipparcos, CC BY-NC 3.0 IGO: commercial use needs ESA's authorisation, see `LICENSE-DATA.md`); both are covered by `.prettierignore`, and `finder-stars.test.ts` asserts their shape and provenance. ## Architecture

Stack and versions: `@README.md`. `output: "server"` — every page and route is SSR by default; no `prerender` flags needed. React islands only where there is client state (forms use `client:load`). shadcn/ui aliases are in `components.json`.

**Request flow**: `@src/middleware.ts` runs on every request, builds a cookie-backed Supabase SSR client, resolves the user into `Astro.locals.user` (typed in `src/env.d.ts`), and redirects unauthenticated requests on a gated path to `/auth/signin`; a GET of a gated page adds `?next=<path+query>`, and sign-in continues there (S-09). `@src/lib/auth-redirect.ts` (`safeNextPath`) is the one rule for what counts as a safe `next`, used by the middleware, the sign-in page and `POST /api/auth/signin`. Gated paths are the `PROTECTED_ROUTES` array in `@src/lib/protected-routes.ts`, matched on whole path segments (`/log` covers `/log/new`, never `/login`); add new ones there. The auth cookies live 30 days from the last token refresh: `@supabase/ssr` ignores `cookieOptions.maxAge` and writes 400 days, so `createClient`'s `setAll` applies `withSessionMaxAge` from `@src/lib/session-cookie.ts`. Password reset (FR-003) is parked: Supabase's built-in email only reaches the project's team. The account plan (F-01) is never read here: the middleware stays free of plan queries.

**Auth surfaces**: pages under `src/pages/auth/`, POST handlers under `src/pages/api/auth/`, React forms under `src/components/auth/`. Forms do client-side validation only and submit as plain HTML POSTs; the server is the source of truth.

**Data access**: the middleware also puts the request-scoped Supabase client on `Astro.locals.supabase` (`null` when unconfigured; gear pages then render `DatabaseMissing`). `@src/lib/gear/` holds `schemas.ts` (zod input schemas shared by forms and routes, island-safe), `store.ts` (every gear DB call, returns fixed value-free message keys), `timezone.ts` (server-only zone resolution) and `eyepiece-presets.ts`. Routes: hub `/gear`, pages `/gear/{sites,telescopes,eyepieces}/{new,[id]}`, POST handlers `/api/gear/<entity>` (create), `/api/gear/<entity>/[id]` (update) and `/api/gear/<entity>/[id]/delete`; on success they redirect to `/gear?saved=<kind>` or `/gear?deleted=<kind>` (`site`, `telescope` or `eyepiece`), which the hub checks against that fixed set and shows as a success `Notice`. Migrations deploy via CI's `migrate` job. The account plan (free or full, FR-045) is server-owned: `account_plans` is read-only for users, only `npm run account:plan` writes it, and `@src/lib/account-plan/` reads it lazily (`getAccountPlan(locals)`, one query per request, only when asked; anything unknown or a failed read is free). Full-plan routes and pages call `requireFullPlan(locals)`, and every Tonight island also reads the plan (`accountPlanForCopy`, the same memoised read, one query per request) for its offline metadata (`data-plan`, so the worker can drop stored finder charts once the plan is lost); nothing else queries the table.

**Location picking** (S-08, roadmap S-09): onboarding and the add/edit site form share `src/components/location/LocationPicker.tsx` ("Use my location", place search, confirmation line); the host form keeps the coordinate fields and validation. Device positions go through `locateDevice` (`src/lib/location/locate.ts`), which asks only on the click and rounds before returning; place search is `src/lib/location/geocode.ts`. A new way to pick a location joins the picker, never a host form. **Pick from map** (roadmap S-09) is the third way: Leaflet 1.9.4 (pinned) with OpenStreetMap's standard tiles, and the click is the user's consent, so before it the page requests no tile, no map code and no map CSS (`tests/e2e/site-map.spec.ts` pins this). `src/components/location/map-panel.tsx` is the only Leaflet importer, loaded by `import("./map-panel")` on the click; it injects `leaflet/dist/leaflet.css?url` as a `<link>` (never a plain CSS import: the build emits one site-wide stylesheet). Picks go through `pickFromMap` (`src/lib/location/map-view.ts`, rounded to 0.01°), and the map recentres on the device only when `geolocationAlreadyGranted` says so (no prompt). `scripts/build-sw.mjs` fails the build if map assets enter the precache, if the `map-panel` chunk is missing, or if leaflet.css lands in a shared stylesheet. Leaflet's chrome is restyled in `global.css` with unlayered, `[data-theme]`-prefixed overrides (leaflet.css loads last and beats Tailwind), tokens only; the tiles are filtered on `.leaflet-tile-pane` in light and dark (the tile `img` filter is `none`, or the red-only filter under an inverted pane turns cyan) and on the tile images in red, through `#red-night-map` in `Layout.astro` (WebKit ignores an SVG filter on the composited pane). `LocationPick.source` includes `{ kind: "map" }`, handled with exhaustive switches at the four host branch points (SiteForm `pickLocation` and its summary, onboarding `pickLocation` and `whereSummary`); hosts pass `current` (`parseCurrent`) and SiteForm's Undo bumps `closeSignal`.

**Gear catalogue (S-12)**: the telescope and eyepiece forms on `/gear` and in onboarding lead with a "Find your model" `forms/Combobox` over a hand-entered catalogue in `src/lib/gear/catalogue/` (island-safe; not the server-only `src/lib/catalogue/` of Messier and stars). `telescopes.json` and `eyepieces.json` are edited by hand from manufacturer pages, never extracted from a database (EU database right): every entry has an https `source`, and `catalogue.test.ts` pins the rules in its `README.md` (names are brand + model + numbers only, ranges, f/3-f/16, estimated AFOVs, zoom click stops, bundled eyepieces, size floors). A pick only fills the form's own fields through `fill.ts`; nothing stores a model id. Each file loads as its own lazy chunk (`load.ts`), so it never sits in a form chunk or the page HTML. Onboarding keeps its fixed generic presets (PRD FR-006) behind "Not sure of the model?", and offers a "Came with <model>" kit from the chosen telescope's `bundledEyepieces`.

**Engine** (`@src/lib/engine/`): pure sky maths over `astronomy-engine`. Inputs are explicit (`Site` with an IANA `timeZone`, `ObservingNight` from `observingNight(date, timeZone)` = local noon to local noon; which night is "tonight" comes from `tonightDateFor` (the night in progress until civil dawn, `TONIGHT_ROLLOVER_SUN_ALTITUDE_DEG`, then the evening ahead), used by Tonight and the log's latest-night check via `src/lib/tonight/tonight-date.ts`, thresholds from `parameters.ts`); outputs are plain data. It must never read the clock, environment, network or filesystem: `purity.test.ts` greps for that and fails the suite. J2000 catalogue coordinates go through `Rotation_EQJ_HOR` + `HorizonFromVector`, never straight into `Horizon()`. Import via the barrel `@/lib/engine`. `fixtures/` is test-only. The PRD's tunable numbers are candidates in `parameters.ts`; do not hardcode them elsewhere.

**Catalogue** (`@src/lib/catalogue/`): `MESSIER` (110 validated objects, NGC 5866 listed as M102) and `findMessier(n)`; `CALDWELL` (61 objects from `caldwell.json`, written by the same `npm run catalogue:build`: Caldwell numbers come from OpenNGC's `Identifiers`, non-Messier, dec ≥ −23°, the Double Cluster's two rows merged as NGC869); `DEEP_SKY` is both lists in one array and `findDeepSky(id)` looks an object up by its id (`M31`, `NGC7000`, `IC405`). Every object has an `id` and a display `label` (the id for Messier, the spaced designation such as "NGC 7000" for Caldwell): views show `label`, never a bare Messier number; `messier` is null for a Caldwell object. `BRIGHT_STARS` in `stars.ts` (the 925 stars to magnitude 4.5 from `bright-stars.json`, built by `npm run stars:build`, J2000 unit vectors; the island-safe entry, never through `./index`), with Polish star names in `star-names.ts`. `finder-stars.ts` is the server-only deeper star field (the 25,791 stars to magnitude 7.5 from `finder-stars.json`, same `stars:build` run, lazy `loadFinderStars()` with `formatDesignation` for "Mirach (β And)"; finder chart, Phase 1), never imported by `stars.ts`, `./index` or an island. Ranking runs over `DEEP_SKY`; `MESSIER_RANK_BONUS` (`parameters.ts`) is an order-only nudge for Messier objects (added to the rank score, never to `score.total`, so it never decides whether an object clears the bar), and `src/lib/engine/calibration.test.ts` guards the mixed ranking on fixed nights and checks each night's top 5 against the committed beginner reference (overlap ≥ 3, `src/lib/engine/fixtures/beginner-reference.ts`; snapshot the top ten per night with `CALIBRATION_SNAPSHOT=1 npx vitest run src/lib/engine/calibration.test.ts --reporter=verbose` when retuning, which is a recording aid, not an oracle). Data files are CC BY-SA 4.0 derived works (see `LICENSE-DATA.md` there; OpenNGC and HYG, with ESA for Hipparcos, are credited in `Attribution.astro`).

**Layout**: `@src/layouts/Layout.astro` wraps every page, renders `<html lang data-theme>` (`dark` default, `light`, `red` night mode) from `Astro.locals.locale`/`theme` (resolved by the middleware from the `sidereus-lang`/`sidereus-theme` cookies, see `@src/lib/preferences.ts`) and renders config-status banners. Type is one self-hosted family, Archivo (`@fontsource-variable/archivo`, imported in `global.css`): expanded for `font-display`, normal width for `font-sans`, and `font-mono` is Archivo with tabular figures. Navigation (top-nav-redesign): the shells (`GearShell`, `AuthShell`, `Welcome`) render `Topbar.astro` (one row: name, then a right-hand cluster of the destinations as a segmented pill from `md` and the `TopbarControls` island with the theme button, which cycles dark → light → red via `nextTheme` (hidden below `sm` when signed out, so the Polish row with the sign-in link fits 320 px), and a native-popover settings panel for theme, language and sign-out) and `TabBar.astro` (bottom tabs below `md`, signed in, not on `/onboarding`); both take the destination list from `@src/lib/navigation.ts`.

**Offline (S-06)**: production builds register a service worker (`src/sw.ts`, bundled by `scripts/build-sw.mjs` in `postbuild`; every decision is a pure function in `src/lib/offline/copies.ts`). It precaches the build's static files and stores each Tonight page the user opens as a pair (the shell plus its server-island response, committed only when that exact island answers 200 with a `data-offline-copy` element) together with a `?night=next` copy for the evening after (rendered from the same forecast, recording no sky check), plus the `/_astro/*` files they need and `/offline`. Tonight navigations are network-first with a ~4 s timeout before the stored copy; any other page that fails at the network gets `/offline`, which lists the stored pages. Signing in, up or out (and the sign-in bounce) purges every copy, and so does any page rendered signed out (`<html data-signed-out>`, which `page-state.ts` reports to the worker) or a commit by a different user: each copy carries `data-owner`, a SHA-256 fingerprint of the user id (`src/lib/offline/owner.ts`, never the id or email itself); a site's copies expire 36 h after its last refresh. A copy served from storage carries `<html data-from-device>`, and `src/lib/offline/page-state.ts` keeps `<html data-offline>` in step with the device, reveals the island's offline notice and disables controls marked `data-needs-network`.

**Copy and formatting** (`@src/i18n/`): every user-facing string is a key in the typed catalogue. `messages/en.ts` is the source; `messages/pl.ts` must have the same keys (`satisfies Messages`, plus a parity test in `i18n.test.ts`). Parameterised messages are functions of a params object whose numbers arrive pre-formatted; plurals go through `plural(locale, n, forms)`. Tonight wording and dates/times/numbers come from `createFormatter(locale)` in `src/lib/tonight/format.ts` (`en-GB` / `pl-PL`, always in the site's time zone); the engine and the locale-fixed formatters in `night.ts`/`zones.ts` stay locale-free. Localised deep-sky common names live in `src/lib/catalogue/common-names.ts`, keyed by object id (`M31`, `NGC7000`), never in the generated JSON. Compass points are the one deliberate exception to the catalogue: the international 16-wind abbreviations (N, NNE … NNW) in every locale, never translated, from `src/lib/compass.ts` (`compassPoint`); never add a localised compass to the catalogues. The finder chart's star designations are the second exception: a Greek letter plus the IAU constellation abbreviation ("Mirach (β And)", `formatDesignation` in `finder-stars.ts`) are never translated; only the 41 star names that `star-names.ts` localises are.

## Conventions

- Import via the `@/*` alias (→ `src/*`). Merge Tailwind classes with `cn()` from `@/lib/utils`, never string concatenation.
- No user-visible literal in templates, islands, schemas or stores: add a key to `src/i18n/messages/en.ts` (and `pl.ts`) and read it via `getMessages(locale)` (compass points excepted: `src/lib/compass.ts`). Zod and store messages are keys; islands translate them with `translateKey`.
- Theme and locale come from `Astro.locals.theme` / `Astro.locals.locale` (never client state or `localStorage`); islands get them as props.
- Colours come from the theme tokens in `src/styles/global.css` only (`bg-surface`, `text-heading`, `text-no-go`, …); `src/styles/no-hardcoded-colors.test.ts` fails on palette classes, hex or `rgb()` anywhere else. A new base token needs a value in every theme block, and the red one must have zero green and blue (`src/styles/red-theme.test.ts`).
- shadcn components go in `src/components/ui/` via `npx shadcn@latest add <name>`. Hooks alias resolves to `src/hooks/` (per `components.json`).
- Observation target keys (`src/lib/targets`, the log's `observations.target`): `M1`–`M110`, `NGC<n>` / `IC<n>` (space-free catalogue ids, no leading zero, up to four digits), the seven planet keys and `moon`. The DB check `observations_target_key` fixes only the shape; whether the catalogue lists the object is the app's `isKnownTarget` in `src/lib/targets/labels.ts`, which the server uses to reject well-formed unknown keys (`NGC1`). The old `observations.messier` column and its sync trigger are gone (dropped in `20261006200000`): write and read `target` only.
- Business logic and services in `src/lib/`. The PRD's scoring engine must be pure and deterministic (identical inputs → identical verdict and ranking), so keep it free of I/O.
- Database changes as Supabase migrations in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`, RLS enabled with per-operation policies. Server-owned tables (`account_plans`) grant users `select` only: writes are revoked from `anon` and `authenticated`, and only the operator's secret key changes them. Per-user isolation is a PRD non-functional requirement and must be testable outside the UI.
- Lint rules live in `@eslint.config.js`; run `npm run lint` before committing.
- Default branch `main`; feature branches `feat/<topic>`; PRs merged via GitHub, by a human only.
