# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Sidereus** — a web app that tells a beginner amateur astronomer whether tonight is worth setting up for (go / marginal / no-go) and which Messier and Caldwell objects to point at, with an eyepiece pair from their own kit. Product requirements, invariants and tunable scoring parameters live in `@context/foundation/prd.md`; the stack rationale in `@context/foundation/tech-stack.md`. Work runs through the 10x `context/` workflow with in-flight changes under `context/changes/<id>/`. **Starting a session: read `context/handoff.md` first** (current state, priorities, next step); the roadmap is `context/foundation/roadmap.md`.

Product code so far: the pure sky engine in `src/lib/engine/` and the generated Messier and Caldwell catalogues in `src/lib/catalogue/` (roadmap F-01, S-03), plus per-user observing sites, telescopes and eyepieces managed under `/gear` (S-01), and the gated `/tonight` dashboard (S-02, S-11): the verdict and dark window over tiles that open focused pages, with every object that cleared the bar ranked on `/tonight/targets` by the engine's pure scoring (`score.ts`, `ranking.ts`, `eyepieces.ts`, `verdict.ts`), with the Open-Meteo forecast behind a Workers KV cache in `src/lib/forecast/` (only `kv-cache.ts` and `observability/rate-limit.ts` import `cloudflare:workers`; tests pass an in-memory cache or mock the module). Tonight also shows the next seven nights at the selected site (S-05): `sevenNightOutlook` in the engine gives nights 1-3 a verdict and nights 4-7 only a cloud outlook, rendered by `NightStrip.astro` on `/tonight/nights` (since tonight-dashboard, `/tonight` is a dashboard of tiles opening focused pages for the targets, the Session plan, the Moon, the planets and the nights). The Session plan (S-05, session-plan-timeline) is `TonightView.sessionPlan`, built only with the `withSessionPlan` option of `loadTonightFor` (the dashboard and `/tonight/plan` pass it): the night from sunset to sunrise on one axis, drawn by `SessionTimeline.astro` on `/tonight/plan` as the night's lines (sunset, dark window, Moon, sunrise, one per line), a legend, and one row per recommended target by best time: "Best 22:40 · window 21:40–23:10 · SW, 45°" above a static server SVG altitude curve (each row carries its `track` of altitudes over the axis and `peakAltitudeDeg`, the plan `minAltitudeDeg` and `trackStep`; the geometry is the pure `src/lib/tonight/altitude-curve.ts`, horizon to zenith on one scale), with the dark window shaded, the minimum altitude dashed, the best window thicker and a dot at best (the dashboard's tile shows only the next target). Tonight shows a Site card and a Telescope card (S-05 / S-08, ui-user-adjustments, `GearCard.astro`), each with a select once the user owns two or more: `?site=<id>` and `?telescope=<id>` on the page shell are remembered in the `sidereus-site` / `sidereus-telescope` cookies and reach the `TonightContent` server island as props (ids only, never coordinates), which resolves them against the user's own sites and telescopes (`src/lib/tonight/gear-choice.ts`, falling back to the oldest). The verdict check (M-2 S-07, `src/lib/sky-checks/`) stores the sky headline each signed-in Tonight view shows in the per-user `sky_checks` table: `TonightContent` calls the `record_sky_verdict` RPC through its shared `defer` (the Worker's `waitUntil`), fire and forget, the one database write from a GET in the app; the RPC is idempotent per (user, site, night) and decides with the database clock, overwriting only before the dark window starts and never after an answer. Tonight's `SkyCheckCard` asks about the newest open night of the last two, and `/log/sky` lists every night whose dark window has started with the tally (`claim.ts` holds the match rule); both post plain Astro forms to `POST /api/log/sky/[id]`.

Sky events (M-3 S-07, sky-events): `skyEvents(site, fromNight, nights, darkThresholdDeg)` (`src/lib/engine/events.ts`, pure; `EVENT_WINDOW_NIGHTS` = 30 nights from the selected one) returns the window's events in moment order: eclipses, greatest elongations and oppositions (searched in `events.ts`), close Moon-planet and planet-planet pairings within 5° computed from the site (`pairings.ts`) and meteor-shower peaks (`meteors.ts`, found by `Search` over the Sun's J2000 longitude, never the of-date `SearchSunLongitude`). **A solar eclipse stays until its partial phase ends** (owner decision A, 2026-10-14): `skyEvents` also returns the previous observing night's solar eclipses whose partial phase ends after the window's start minus 12 h (so the morning eclipse of day D is still returned for the night of D after dawn, with its own earlier `night`), and stays free of the clock. **Visibility and the invariant:** every event carries `visibility`, decided in one place (`visibleAt`: at or above 10° at a sampled moment of the night's dark window, or its twilight span flagged `shortNight`, with the Sun at or below −6°; `eclipseVisibility`: from 2°, "low, needs an open horizon" under 10°; `best` is the peak when the peak is up, else, for a `partly` visible eclipse, the moment the body clears 2° while the phase is still in progress, bisected between the peak and the highest contact, never the contact itself), and only visible events are ever worded as something to go out for (PRD invariant, US-07): the tile, the verdict line and every "best time" read `isNotableEvent` (visible, not a penumbral lunar eclipse). A shower peak is a night, never a minute: the radiant is judged on the peak night, else the night before or after (`bestNight`), and the shower counts for `tonight` and `next` on that best night (`goNight`; the page still groups its row by the peak night, and `meteorEvents` keeps a peak from the two days before the window when its best night is the window's first). The shower table, `src/lib/catalogue/meteor-showers.ts` (keys typed by `SHOWER_KEYS` / `ShowerKey`, which also type `tonight.events.showerName` and `showerNameInLine` in both languages; the bright-Moon note shows on a visible shower only), is eight showers entered by hand as rounded facts (peak night and rate from NASA's pages, radiant and speed from the IAU MDC, each cross-checked; nothing from the IMO, whose list needs written permission; peak longitudes derived by our engine, not copied); its licence note is `LICENSE-DATA.md` ("Meteor showers", not legal advice) and `Attribution.astro` credits both. A solar eclipse row, visible or not, always carries the fixed eye-safety line (`tonight.events.solarSafety`); the tile and the verdict line say "eclipse glasses only". `TonightView.skyEvents` exists only with the `withSkyEvents` option of `buildTonight` / `loadTonightFor` (a failure logs the `tonight.sky-events` step through `logFailure` and drops only that block): `formatSkyEvents` (`src/lib/tonight/sky-events.ts`, which takes the request's `now`; `buildTonight` passes the real one, and the next night's sunset for `night: "next"`) words the events into `events`, `tonight` (notable visible events whose go night is the selected one, solar eclipses first, then by moment, so "eclipse glasses only" never hides behind "+N more") and `next` (the earliest from it on, a solar eclipse winning a tie). A solar eclipse whose partial phase ended before `now` is dropped from all three; one still to come counts in `tonight` (and as `next`) when its local date, in the site's zone, is today or its night is the selected one, and its day is worded from today's date, not from the observing night: `dayWord` (`today` or `tomorrow`) and `at` (the best time, the peak when that is visible), "Today, 11:22" / "Tomorrow, 11:22" (Polish "Dziś, 11:22" / "Jutro, 11:22"), and "Today, 17:04" for an afternoon eclipse on its own day instead of "Tonight" (the tile writes them lowercase between its separators, "· tomorrow, 11:22 ·", like "tonight"); a later day reads its day and time. `/tonight/events` (`EventsPageContent`, `SkyEventList`) lists the whole window by night and is the seventh entry of `TONIGHT_PAGES`. On the dashboard `EventsTile` is the second tile, always shown: `next` ("Perseids peak · night of 12/13 Aug", `eventsTileLine`; `eventsTile` gives `{ line, kind }` and the line leads with `next`'s kind icon) or "Nothing to go out for in the next 30 nights". On an event night `VerdictCard`'s `event` prop adds one muted `Fact` under the reason, led by its event kind's icon (`eventsVerdict` gives `{ line, kind }`), "Tonight: <name>" plus "+1 more" (`eventsVerdictLine`, `data-verdict-event`, no link; a solar eclipse reads "Today, 11:22: …" or "Tomorrow, 11:22: …" from `dayWord` and `at`, and every other event uses its in-sentence `verdictName`, Polish lowercase after the colon: "Dziś: maksimum Orionidów", "Dziś: opozycja Marsa", "Dziś, 11:22: częściowe zaćmienie Słońca, tylko przez okulary do zaćmień"; the Polish titles carry no colon ("Opozycja Marsa", "Największa elongacja Merkurego"), per-key records `elongationName` / `oppositionName` and their `…InLine` forms, never a grammar function; owner, 2026-10-14): no room is reserved (the owner accepts the one-line shift, plan review F3), `VERDICT_MIN_HEIGHT_CLASS` and the skeleton carry the re-measured `min-h-42 sm:min-h-58` (2026-10-15) with nothing added for the event line, and `tonight-phone.spec.ts` hides the line (`[data-verdict-event]{display:none}`) while it measures the cards. The kind icons and the visible / not-visible mark icons (`CircleCheck` / `CircleSlash`) come from the shared map in `fact-icons.ts`, and each detail, the visibility sentence, the notes and the safety line are one `Fact` each. `/design` pins the line, the tile and a `SkyEventList` window (30 nights from 2027-07-25 at Warsaw, with the 2027-08-02 solar eclipse) from fixed data (`src/components/design/event-samples.ts`).

Finder chart (M-3 S-03, finder-chart): `/tonight/finder?object=M31&from=targets|planets|plan` (plus the usual `?site=`, `?telescope=`, `?night=`; `finder.astro` shell + `FinderContent` server island, components in `src/components/finder/`) is the first full-plan page, opened by the "Finder chart" quiet link on every `ObjectDetails` and `PlanetCard` (never the Moon's) for every account. The plan is checked twice: the shell calls `requireFullPlan` (a free or signed-out visitor gets `FinderLocked`, the explainer with the fixed precomputed `EXAMPLE_FINDER_CHART`, and no island), and the island's loader `loadFinderFor` (`src/lib/finder/load.ts`) calls it again before it reads Tonight or the star file, because `/_server-islands/*` is not behind the middleware and an island URL replays without the session; `scripts/smoke.mjs` proves both layers over HTTP (test-plan 6.4). The page never redirects: every state (`chart`, `locked`, `not-ranked`, `no-gear`, `failed`) is a 200 marked `data-finder-state`, and only the chart state's root carries `data-finder-chart` (never inside `FinderChart`, which the free example renders too). The chart is a static server-rendered SVG, two panels (overview from the start star to the target with the numbered hop, and the finder's 7° field with the finder circle, reflex rings and the finding eyepiece's circle) built by the pure engine `finderChart` (`src/lib/engine/finder.ts`; stars come in as an argument) from the deeper star file (`loadFinderStars()`, 25,723 stars to magnitude 7.5, server-only, a dynamic `import()`; no star data reaches the browser and `build-sw.mjs` fails the build if `finder-stars` lands in `dist/client`); geometry in `src/lib/finder/chart-svg.ts`, the sentences in `steps.ts`. The start star is the nearest one above the site's minimum altitude and no fainter than `startStarMaxMagForBortle` (4.5 / 3.5 / 2.5, never above the naked-eye limit); the hop is the exact layered search of `parameters.ts`'s `HOP_*` candidates. **Overhead rule:** when either panel's centre is at or above `FINDER_OVERHEAD_ALT_DEG` (80°) or the zenith falls inside a panel, both panels switch to the pole as "up" (`data-finder-orientation="overhead"`, a zenith cross in a panel that holds the zenith or an arrow on the panel's edge pointing toward it (`zenithEdge`, owner decision 2026-10-13), "Nearly overhead" instead of a compass point); otherwise `facing`, "up" being the vertical through each panel's centre. Every way to `failed` leaves a `logFailure` line (`finder.stars`, `finder.chart`, `finder.tonight`) and renders `failed`. **Offline storage and the plan-loss drop** (O-4, D-13 to D-15): a chart opened online by a full-plan user is stored as a pair like the Tonight pages, keyed by `(siteId, page, target, kind)` (`storedPageOf`, `copyMetaFor` and `dropFinderCopies` in `src/lib/offline/copies.ts`; no next-night copy, no prefetch, listed on `/offline`); every Tonight island's `OfflineCopy` (and the locked finder root) carries `data-plan="full|free|unknown"` and `data-plan-at` (when the plan was read, server clock) from `accountPlanForCopy`, and the worker drops every stored chart only on an explicit `free` (a failed plan read is `unknown`, logged with its code: it neither stores nor drops charts), at the first online Tonight or finder answer after the plan is lost; `freeSince` (the newest free answer's plan-read time, never the device clock) refuses a chart whose plan was read before it. Charts expire 36 h after the site's last refresh and go with sign-out like the other copies.

What to expect (M-3 S-04, what-to-expect): each ranked deep-sky target on `/tonight/targets` and its finder chart says in one sentence what it will look like in the user's own telescope from their site. The rule is the pure `expectationFor(object, bortle, apertureMm)` in `src/lib/engine/expectation.ts`, one of 22 `ExpectationKey`s (`EXPECTATION_KEYS`; no Moon input, the line is a property of object, site and telescope): a contrast deficit (the core surface brightness, from `coreSurfaceBrightness` in the shared `src/lib/engine/contrast.ts` (which also holds `contrastDeficit`, `contrastBand` and `telescopeLimitingMag`): the flat `effectiveSurfaceBrightness` offset, plus `EXPECT_BULGE_CORE_EXTRA_MAG` = 0.8 mag for bulge-type spirals, chosen by OpenNGC's `hubble` type in `BULGE_HUBBLE_TYPES`; the washed-out rule in `score.ts` keeps plain `effectiveSurfaceBrightness`; minus the moonless zenith sky for the Bortle class, less an aperture term of 0.5 mag per doubling from 150 mm) falls into four bands (`bright`, `smudge`, `faint`, `limit`; `contrastBand`, after a near-limit floor that makes an object within 1 mag of `telescopeLimitingMag` at least `faint`), and a per-type table turns the band into the key (galaxies, nebulae, planetaries, globulars by aperture and headroom, open clusters by size, with fixed keys for M24, M40 and M73). Its numbers are the `EXPECT_*` candidates after `WASHED_OUT_TYPES` in `parameters.ts`. `src/lib/engine/fixtures/expect-reference.ts` (test-only, not in `fixtures/index.ts`) is the source-cited reference: showcase entries and hard cases (M42 under Bortle 7, M56 at 200 mm, the Helix and the Owl, NGC 7000, a faint galaxy near 11 mag, M33 at Bortle 9, and the small-scope hard cases M31 at 60 mm / Bortle 5, 6 and 8, M33 at 80 mm / Bortle 4, M81 at 80 mm / Bortle 5, M101 at 80 mm / Bortle 3 and 6), 28 references in all (M106 at 150 mm / Bortle 5 joined them in openngc-galaxy-magnitudes), each with at least two published sources, and `KNOWN_DIVERGENCES` for the entries the rule still gets wrong (NGC 7000, NGC 4889, M33 at 80 mm / Bortle 6 and M106 at 150 mm / Bortle 6; the list is full at the test's cap of 4, so a new diverging reference needs a rule fix or an owner decision about the cap; the cap went 3 → 4 on the owner's permission of 2026-10-19). The V magnitude of 12 galaxies that OpenNGC gets wrong (its V-Mag is HyperLEDA's `vt`, or the generator had copied B) is derived in the generator from B and the median colour of the catalogue's own credible galaxies of the same Hubble group (follow-up #178; at 150 mm / Bortle 6 M106 stays `galaxyFaint`, the deficit 1.61 against the 1.5 edge); a failing reference is an engine finding, never a fixture edit. The phrases are `tonight.expect.phrase[key]` in `en.ts` / `pl.ts` (plus `locked` and `lockedFinderLine`). The server helper `src/lib/tonight/expectation.ts` (`expectationKeyFor`, `expectationText`, `expectationView`) is the gate: a confirmed full plan (`getAccountPlan`, which fails closed) gets the lines, an explicit `free` read gets one muted locked line under the Targets count, and a failed read (`unknown`, from `accountPlanForCopy`) gets neither, so a paying user is never told they lack the plan because of a transient error. The key is computed only in the Targets island (`TargetsPageContent`, passed down through `ObjectCard` / `ObjectRow` to `ObjectDetails`) and in `loadFinderFor`'s `chart` state (`expectation`, after the plan guard; a planet's chart shows its existing free `note` from `view.solarSystem`), never in `TonightView` or `loadTonightFor`, so a free account's island HTML never holds a phrase and a leaked island URL renders nothing signed out. Markers: `<div data-expect="<key>">` (a `Fact` root; a planet's own key on its chart) and `<p data-expect-locked>`; matching the valued `data-expect="` matters because the bare attribute is a substring of the locked one. `scripts/smoke.mjs` proves the gate over HTTP (`expect 1` free, `expect 2` full, `finder 3`, `expect 3` signed out, from the Targets island URL captured off its shell) and `tests/e2e/what-to-expect.spec.ts` in the browser. **Offline** (owner decision O-2): a stored Targets copy keeps its lines until the next online visit replaces it, its next-night copy is refreshed, or it expires 36 h after the site's last refresh; there is no plan-loss drop for Targets pages (only finder charts have one), since the text derives from public catalogue data and the user's own gear.

Adjustable session plan (M-3 S-08, adjustable-session-plan): a full-plan user edits tonight's Session plan on `/tonight/plan` (move up or down, remove, add, one Save), and the list is stored in `public.session_plans`, one row per user, site and night (`targets text[]`, the whole ordered list; unique `(user_id, site_id, night)`; RLS with the four `_own` policies, insert and update also check that the site is the owner's, as `sky_checks` does; `on delete cascade` from the site; checks on count, shape and the catalogue's key pattern; `tests/db/tables.ts` takes it through the `needsSite` option and `tests/db/session-plans.test.ts` pins the rest). The guardrail is that a row exists only when the engine's own rule gave the key a window tonight: the pure `applyPlanEdits` (`src/lib/tonight/plan-edits.ts`) builds the rows only from the suggested plan or from `rankObjects`' `reachable` list (every catalogue object the telescope can reach, each with its best window, including below-bar and washed-out ones; the saved list itself never makes a row), and a saved key with no window tonight goes to `notTonight` (muted "Not on tonight's plan", kept until removed). `src/lib/tonight/plan-window.ts` (`deepSkyWindow`, `solarSystemWindow`, `planetWindowFor`) is the window rule of the build's planet window (`planetWindowFor`) and the save route's check of newly added keys (`keysWithoutWindow` in `src/lib/session-plans/checks.ts`); `solarSystemWindow` is held to the build's planet and Moon rule by the parity test `plan-window.test.ts`, not by shared code; a key already on the stored list is never re-checked (F4), so a list stays saved after the site's minimum altitude rises. `loadTonight` computes the night date once (`tonightDateForSite`, plus one day for `night: "next"`) and passes it to `readPlanEdits` and to `buildTonight`; edits and the editor exist for tonight only (D9), and both routes compare the posted night with `tonightDateForSite(site, now)` (`errors.sessionPlan.nightOver`). **Gates:** both routes call `requireFullPlan` before any read or write; ## Architecture

Stack and versions: `@README.md`. `output: "server"` — every page and route is SSR by default; no `prerender` flags needed. React islands only where there is client state (forms use `client:load`). shadcn/ui aliases are in `components.json`.

**Request flow**: `@src/middleware.ts` runs on every request, builds a cookie-backed Supabase SSR client, resolves the user into `Astro.locals.user` (typed in `src/env.d.ts`; `sessionUser` in `src/lib/auth/session-user.ts` reads the `error` of `getClaims()` too: a stale cookie signs the user out quietly, an Auth outage, timeout or unknown error leaves an `auth.claims` line), and redirects unauthenticated requests on a gated path to `/auth/signin`; a GET of a gated page adds `?next=<path+query>`, and sign-in continues there (S-09). A signed-in GET of `/auth/signin` or `/auth/signup` (`isAuthEntryPath`) is redirected off at once, to the safe `next`, else `/tonight`; sign-up carries `next` through `withNext` (sign-up form, `POST /api/auth/signup`, `/onboarding?next=…`, the onboarding form and `POST /api/onboarding`, which ends on `next`; the confirm-email page keeps it for "back to sign in"), so a new user finishes first-run setup before reaching the page they asked for (M-4 S-06). `@src/lib/auth-redirect.ts` (`safeNextPath`) is still the one rule for what counts as a safe `next`, used by the middleware, the sign-in and sign-up pages and the auth and onboarding routes. Gated paths are the `PROTECTED_ROUTES` array in `@src/lib/protected-routes.ts`, matched on whole path segments (`/log` covers `/log/new`, never `/login`); add new ones there. The auth cookies live 30 days from the last token refresh: `@supabase/ssr` ignores `cookieOptions.maxAge` and writes 400 days, so `createClient`'s `setAll` applies `withSessionMaxAge` from `@src/lib/session-cookie.ts`. Password reset (FR-003) is parked: Supabase's built-in email only reaches the project's team. The account plan (F-01) is never read here: the middleware stays free of plan queries.

**Auth surfaces**: pages under `src/pages/auth/`, POST handlers under `src/pages/api/auth/`, React forms under `src/components/auth/`. Forms do client-side validation only and submit as plain HTML POSTs; the server is the source of truth.

**Data access**: the middleware also puts the request-scoped Supabase client on `Astro.locals.supabase` (`null` when unconfigured; gear pages then render `DatabaseMissing`). `@src/lib/gear/` holds `schemas.ts` (zod input schemas shared by forms and routes, island-safe), `store.ts` (every gear DB call, returns fixed value-free message keys plus a sanitized `fault` the route logs through `saveFailureKey`), `timezone.ts` (server-only zone resolution) and `eyepiece-presets.ts`. Routes: hub `/gear`, pages `/gear/{sites,telescopes,eyepieces}/{new,[id]}`, POST handlers `/api/gear/<entity>` (create), `/api/gear/<entity>/[id]` (update) and `/api/gear/<entity>/[id]/delete`; on success they redirect to `/gear?saved=<kind>` or `/gear?deleted=<kind>` (`site`, `telescope` or `eyepiece`), which the hub checks against that fixed set and shows as a success `Notice`. Migrations deploy via CI's `migrate` job. The account plan (free or full, FR-045) is server-owned: `account_plans` is read-only for users, only `npm run account:plan` writes it, and `@src/lib/account-plan/` reads it lazily (`getAccountPlan(locals)`, one query per request, only when asked; anything unknown or a failed read is free). **Engine** (`@src/lib/engine/`): pure sky maths over `astronomy-engine`. Inputs are explicit (`Site` with an IANA `timeZone`, `ObservingNight` from `observingNight(date, timeZone)` = local noon to local noon; which night is "tonight" comes from `tonightDateFor` (the night in progress until civil dawn, `TONIGHT_ROLLOVER_SUN_ALTITUDE_DEG`, then the evening ahead), used by Tonight and the log's latest-night check via `src/lib/tonight/tonight-date.ts`, thresholds from `parameters.ts`); outputs are plain data. It must never read the clock, environment, network or filesystem: `purity.test.ts` greps for that and fails the suite. J2000 catalogue coordinates go through `Rotation_EQJ_HOR` + `HorizonFromVector`, never straight into `Horizon()`. Import via the barrel `@/lib/engine`. `fixtures/` is test-only. The PRD's tunable numbers are candidates in `parameters.ts`; do not hardcode them elsewhere. A galaxy's brightness score component is capped by its contrast band (small-scope-galaxies, `brightnessOf` in `score.ts`): full credit at `bright` and `smudge`, `GALAXY_FAINT_BRIGHTNESS_CAP` = 0.1 at `faint`, `GALAXY_LIMIT_BRIGHTNESS_CAP` = 0 at `limit`, so the reason line "Bright for your N mm" always agrees with the what-to-expect line; `src/lib/engine/small-scope.test.ts` (G1-G6) guards it. By owner decision (2026-10-15, plan review F6), in a 60-80 mm under city skies (Bortle 7-8) M31 reads "very faint" (`galaxyFaint`) and leaves the top 5; do not "fix" that. **Duration, window edges and reasons** (M-4 S-05, evening-showpieces): `duration` is `min(1, windowMinutes / DURATION_USEFUL_SPAN_MINUTES) × mean placement over the window` (`score.ts`, span 120 min, a named candidate; window minutes come from the window's sample times, a one-sample window is 0, and it does not depend on the aperture), so a pass that fills 4 h of a 6 h night scores like one that fills 4 h of a 12 h night; by owner decision OD-1 that removes only the structural penalty, and October's M13 (about #31), M15 (#19) and M57 (#46) stay outside the top 5: a known divergence, not a bug to fix with a bonus. A deep-sky window's edges are the true crossings of the minimum altitude, not the 10-minute samples: `refinedWindow(track, min)` in `objects.ts` (linear interpolation between the two samples around a crossing, plus `firstIndex` / `lastIndex` of the sample run) is used by `scoreObject` and `deepSkyWindow` only; `bestWindow` and the planet and Moon windows keep grid edges. **Scores stay on the grid and the text uses the refined edges**: `scoreObject` reads the window's samples (`firstIndex`..`lastIndex`), never the refined edges, so refining cannot move a rank, while `ObjectScore.window`, Targets, the Session plan and the reason line show the true edges, so a one-sample window reads "Up for 14 min" with a duration of about 0. `reasonComponents` (`ranking.ts`) names a component for an entry only when it is eligible (`duration` and `brightness` always; `moon` and `sky` only when the listed entries differ on it by at least `REASON_MIN_SPREAD` = 0.05, so a new-Moon night never says anything about moonlight) and the entry is at or above the list mean on it (the one exception, owner decision 2026-10-16: when nothing is named for an entry its lead is its largest weighted eligible component, which may sit below the mean, and it has no second); `secondComponent` is `ScoreComponent | null` and `reasonLine` prints one phrase when there is no second. The window edges are checked against Skyfield + DE421: `scripts/deep-sky-reference.py` wrote `src/lib/engine/fixtures/skyfield/deep-sky-warsaw-2026.json` for all 171 `DEEP_SKY` objects on Warsaw 2026-04-15, 2026-07-15 and 2026-10-15, and `window-reference.test.ts` holds the engine's windows to it within 5 minutes and 1° (PRD criterion 2's ephemeris leg also covers each night's top 5); a failing reference is an engine finding, never a fixture edit.

## Conventions

- Import via the `@/*` alias (→ `src/*`). Merge Tailwind classes with `cn()` from `@/lib/utils`, never string concatenation.
- No user-visible literal in templates, islands, schemas or stores: add a key to `src/i18n/messages/en.ts` (and `pl.ts`) and read it via `getMessages(locale)` (compass points excepted: `src/lib/compass.ts`). Zod and store messages are keys; islands translate them with `translateKey`.
- Theme and locale come from `Astro.locals.theme` / `Astro.locals.locale` (never client state or `localStorage`); islands get them as props.
- Colours come from the theme tokens in `src/styles/global.css` only (`bg-surface`, `text-heading`, `text-no-go`, …); `src/styles/no-hardcoded-colors.test.ts` fails on palette classes, hex or `rgb()` anywhere else. A new base token needs a value in every theme block, and the red one must have zero green and blue (`src/styles/red-theme.test.ts`).
- shadcn components go in `src/components/ui/` via `npx shadcn@latest add <name>`. Hooks alias resolves to `src/hooks/` (per `components.json`).
- Observation target keys (`src/lib/targets`, the log's `observations.target`): `M1`–`M110`, `NGC<n>` / `IC<n>` (space-free catalogue ids, no leading zero, up to four digits), the seven planet keys and `moon`. The DB check `observations_target_key` fixes only the shape; whether the catalogue lists the object is the app's `isKnownTarget` in `src/lib/targets/labels.ts`, which the server uses to reject well-formed unknown keys (`NGC1`). The old `observations.messier` column and its sync trigger are gone (dropped in `20261006200000`): write and read `target` only.
- Business logic and services in `src/lib/`. The PRD's scoring engine must be pure and deterministic (identical inputs → identical verdict and ranking), so keep it free of I/O.
- Database changes as Supabase migrations in `supabase/migrations/` named `YYYYMMDDHHmmss_short_description.sql`, RLS enabled with per-operation policies. Server-owned tables (`account_plans`) grant users `select` only: writes are revoked from `anon` and `authenticated`, and only the operator's secret key changes them. Per-user isolation is a PRD non-functional requirement and must be testable outside the UI.
- Lint rules live in `@eslint.config.js`; run `npm run lint` before committing.
- Default branch `main`; feature branches `feat/<topic>`; PRs merged via GitHub, by a human only.
