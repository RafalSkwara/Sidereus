# Verified Ephemeris Core Implementation Plan

## Overview

Build the pure, deterministic sky-maths foundation that every ranking slice will stand on: a licensed, reproducible Messier catalogue derived from OpenNGC, and an engine module that, for a site and an observing night, computes the dark window (sun below a Bortle-dependent threshold), moon altitude/illumination/separation, and the altitude and azimuth of any fixed deep-sky object over the night. Results are asserted against values read from Stellarium within the PRD's candidate tolerance (1 degree of altitude, 5 minutes of time), under a Vitest harness that the repo currently lacks. This is roadmap item **F-01** (`verified-ephemeris-core`); it contains no scoring, no verdict, no forecast, no persistence and no UI.

## Current State Analysis

- The codebase is the untouched starter plus `context/`: auth pages, a dashboard placeholder, and `src/lib/{supabase,utils,config-status}.ts`. No product code, no `src/lib/engine`, no catalogue data.
- **No unit test runner.** `package.json` scripts are `dev/build/preview/astro/lint/lint:fix/format/smoke`. CI (`.github/workflows/ci.yml`) runs `npm ci → astro sync → lint → astro check → build` in the `ci` job and an HTTP smoke walk in the `smoke` job. `coverage/` is already git-ignored.
- Toolchain: Astro 7.3.2, Vite 8.3.0, `@astrojs/cloudflare` 14.3.1, TypeScript 6.0.3, Node ≥ 24.16. `tsconfig.json` includes `**/*`, so `*.test.ts` files are already inside the type-checked lint project (typescript-eslint `projectService`).
- Lint is `strictTypeChecked` + `stylisticTypeChecked`; `no-console` warns everywhere except `scripts/**/*.mjs`, which has its own relaxed block in `eslint.config.js` (`scriptsConfig`, globals `console, process, fetch, URLSearchParams`).
- PRD contracts this module must honour: determinism NFR (identical inputs → identical output), ephemeris tolerance NFR (candidate 1° / 5 min, Open Question 9), Business Logic invariant 1 (object below the site's minimum altitude never ranks — needs correct altitude), darkness threshold by Bortle (Open Question 7: −18° for Bortle 1-4, −15° for 5-6, −12° for 7-9), the "no dark window this season" case (FR-023), site-local time across the 2026-10-25 DST transition, and attribution of licensed data sources.
- The roadmap places the coordinate→timezone lookup in S-01 and the seasonal forward search ("date the dark window returns") in S-04; this foundation provides the primitives only.

### Key Discoveries:

- OpenNGC `database_files/NGC.csv` is **semicolon-delimited**, header `Name;Type;RA;Dec;Const;MajAx;MinAx;PosAng;B-Mag;V-Mag;…;SurfBr;…;M;NGC;IC;…;Common names;…`. RA is `HH:MM:SS.ss`, Dec is `±DD:MM:SS.s` (J2000). 107 rows carry an `M` value; `database_files/addendum.csv` (same header) adds `M040` (type `**`, no size), `Mel022` (M45 Pleiades, type `OCl`) and `M102` (type `Dup`, `M=101`, "identification is controversial"). NGC 5866 (`NGC5866`, V 9.89, SurfBr 23.40) has an empty `M` column and must be overridden to M102 per the planning decision.
- 71 of 110 Messier objects have no `SurfBr`; M73 and M40 have no `MajAx`; V-Mag is present for all real rows. Constellation codes are IAU 3-letter, except Serpens appears as `Se1` / `Se2` (Caput/Cauda) and must be normalised to `Ser`.
- OpenNGC `master` at planning time: commit `da90466031b0372c896588b85be6016c617e205b` (2026-07-26). Licence CC BY-SA 4.0 (README lines 15-16); NED, SIMBAD and HEASARC acknowledgements are requested in the README.
- `astronomy-engine` 2.1.19, MIT, zero dependencies, ESM + types shipped, accuracy ±1 arcminute vs NOVAS/JPL. `SearchAltitude(body, observer, direction, dateStart, limitDays, altitudeDeg)` returns **`null` when the altitude is never reached in the window** — this is the FR-023 signal, not an error. `Illumination(Body.Moon, time).phase_fraction` is the illuminated fraction. `AngleBetween(vecA, vecB)` gives separation from two vectors. `Horizon(time, observer, ra, dec, 'normal')` expects **of-date** equatorial coordinates; J2000 catalogue positions go through `Rotation_EQJ_HOR(time, observer)` + `HorizonFromVector(vec, 'normal')` instead (see Critical Implementation Details). `SearchHourAngle` returns an `HourAngleEvent` with `.hor.altitude`, so the sun's minimum altitude needs no second call. `SearchAltitude` is documented as unreliable near a body's minimum or maximum altitude. `DefineStar` has only 8 slots and is not suitable for a 110-object loop.
- Vitest 5 (peer `vite ^6.4 || ^7 || ^8`) configures for Astro via `getViteConfig` from `astro/config` (`/// <reference types="vitest/config" />`). Known adapter-interference issues were fixed in Astro 6/7.0.6; if the Cloudflare Vite plugin still interferes, pass `{ adapter: undefined }`-style overrides as `getViteConfig`'s second argument.
- Workers runtime and Node 24 both ship full `Intl` timezone data, so the noon-to-noon night window can be derived with `Intl.DateTimeFormat(...).formatToParts` and no timezone library.

- No forward search for "the date the dark window returns" — S-04 iterates this module's `darkWindow` over successive nights.
- No coordinate→timezone lookup — S-01 supplies an IANA zone id with each site; the engine takes it as input.
- No compass-point formatting ("SW"), constellation full names, or any display concern — S-02.
- No persistence, migrations, API routes, or UI.
- No CI deploy job or preview environments — F-02. This plan only adds the one-line `npm test` step to the existing `ci` job (repo rule in `CLAUDE.md`: a new test framework must be wired into CI).
- No southern-hemisphere fixture (declined: the persona is suburban Europe; sign errors are covered by Tromsø's high latitude and by synthetic monotonicity tests).
- No scripted Stellarium export; reference values are read by hand per the documented protocol.
- No refraction model choice beyond astronomy-engine's `'normal'`; fixtures record Stellarium's *apparent* altitude to match.

## Implementation Approach

One new runtime dependency (`astronomy-engine`), one new dev dependency (`vitest`), one build-time script. The catalogue is generated once by a script and **committed** as a small JSON (110 rows) so the runtime never fetches or parses CSV; the script pins the OpenNGC commit and is idempotent, so a licence-compliant refresh is a re-run plus a diff. The engine lives in `src/lib/engine/` as small pure modules with explicit inputs (site, night, threshold) and `Date`/number outputs; nothing reads the clock, environment or network, which is what makes determinism testable. Verification is two-layered: synthetic tests that need no external truth (monotonic sun altitude, window inside night, null threshold at Tromsø, determinism, idempotent generator) run from phase 2 on; Stellarium fixtures are filled by the user at the phase 2 and phase 3 manual gates and asserted within named tolerance constants. Fixtures not yet captured surface as `test.todo`, never as silent passes.

## Critical Implementation Details

**J2000 catalogue coordinates never go straight into `Horizon()`.** astronomy-engine's `Horizon()` treats the supplied RA/Dec as equator-of-date; catalogue coordinates are J2000, and passing them unrotated costs ~0.4° in 2026, silently eating most of the 1° tolerance. Use the library's direct frame rotation instead of a manual precession chain: per time step, `vec = VectorFromSphere(new Spherical(decDeg, raHours * 15, 1), time)`, `hor = RotateVector(Rotation_EQJ_HOR(time, observer), vec)`, then `HorizonFromVector(hor, 'normal')`, which returns altitude in `lat` and azimuth (clockwise from north) in `lon`. Compute the rotation matrix once per time step and reuse it across all 110 objects. For the Moon, `Equator(Body.Moon, time, observer, true, true)` followed by `Horizon(time, observer, eq.ra, eq.dec, 'normal')` is correct as-is because `ofdate = true` already returns of-date coordinates.

**`SearchAltitude` semantics and its blind spot.** Search the dusk crossing with direction −1 from `night.start` with `limitDays = 1`, then the dawn crossing with direction +1 from the dusk instant. A `null` dusk result means the threshold is never reached that night (Tromsø in June at −18°): return the `none` variant carrying the sun's minimum altitude at lower culmination, read directly from `SearchHourAngle(Body.Sun, observer, 12, night.start, +1).hor.altitude` (no extra call needed), which S-04 needs for its explanation. A found dusk with a `null` dawn inside the window is clamped to `night.end` and flagged. The library documents that `SearchAltitude` "will not work reliably for altitudes at or near the body's maximum or minimum altitudes": Warsaw around midsummer, where the sun bottoms out near −14° to −15°, is exactly that case for the −15° and −12° thresholds. F-01's fixtures are clear of it (Tromsø's sun stays above the horizon; Warsaw in October bottoms out below −45°), but the `darkWindow` implementation should compare the threshold against the lower-culmination altitude first and return `none` without searching when the minimum is above the threshold, so S-04's seasonal forward search inherits a safe primitive.

**Local noon without a timezone library.** Compute the UTC instant whose wall clock in the IANA zone reads 12:00 on date D: start from `Date.UTC(D, 12:00)`, read the zone's offset at that instant via `Intl.DateTimeFormat(..., { timeZone, hourCycle: 'h23', ... }).formatToParts`, subtract it, and re-check once (noon is never inside a DST transition, so one correction suffices). Reuse the same helper to format fixture times for comparison.

**Fixture time comparison.** Compare instants as epoch milliseconds, never as formatted strings; the 2026-10-24 Warsaw night contains a repeated 02:00–03:00 local hour.

**File**: `scripts/build-catalogue.mjs`

- Emits `src/lib/catalogue/messier.json` (array sorted by Messier number, stable key order, 2-space indent, trailing newline) and `src/lib/catalogue/messier.meta.json` (`source`, `commit`, `licence: "CC BY-SA 4.0"`, `retrievedAt` set from the pinned commit date `2026-07-26`, not from the clock, `overrides` list, `typeMap`). Fails with a non-zero exit if the count is not 110 or any Messier number is missing/duplicated.
- Both generated files are listed in a new root `.prettierignore` (created in this phase) so lint-staged's `prettier --write` on `*.json` cannot reformat them after the first commit; criterion 1.2's byte-identical regeneration depends on this.

#### 5. Catalogue module and types

**File**: `src/lib/catalogue/index.ts`

**Intent**: Typed access to the committed catalogue for the engine and later slices.

**Contract**:

```ts
export type MessierType = "galaxy" | "globular-cluster" | "open-cluster" | "planetary-nebula" | "nebula"
  | "emission-nebula" | "reflection-nebula" | "supernova-remnant" | "cluster-with-nebula"
  | "asterism" | "double-star" | "other";
export interface MessierObject {
  id: `M${number}`;          // "M31"
  messier: number;           // 31
  designation: string;       // "NGC 224" | "IC 4715" | "Mel 22" | "M40"
  commonName: string | null;
  type: MessierType;
  raHours: number;           // J2000, [0, 24)
  decDeg: number;            // J2000, [-90, 90]
  constellation: string;     // IAU 3-letter, "Ser" normalised

  minorAxisArcmin: number | null;
  vMag: number;
  bMag: number | null;

}
export const MESSIER: readonly MessierObject[];
export function findMessier(n: number): MessierObject | undefined;
```

The JSON import infers loose types (`type: string`, `id: string`), so the module validates the imported array at load time (count 110, id shape, `type` within the union, numeric ranges) and exports it through the validator's return type rather than a bare `as` cast; an unknown `type` string therefore fails at import, not at first use.

## Phase 2: Night model, sun events and dark window

### Overview

Define the site and observing-night contracts, compute sun events and the Bortle-threshold dark window including the never-reached case, and lay down the fixture schema and capture protocol. Synthetic tests run green; the manual gate is the user's first Stellarium reading (sun values).

### Changes Required:

#### 1. Engine types

**File**: `src/lib/engine/types.ts`

**Intent**: One vocabulary for every downstream slice.

**Contract**:

```ts
export interface Site { latitudeDeg: number; longitudeDeg: number; elevationM?: number; timeZone: string /* IANA */ }
export interface ObservingNight { date: string /* YYYY-MM-DD evening date, site-local */; timeZone: string; start: Date /* local noon D */; end: Date /* local noon D+1 */ }
export interface Interval { start: Date; end: Date }
export type DarkWindow =
  | { kind: "window"; thresholdDeg: number; start: Date; end: Date; clampedToNightEnd: boolean }
  | { kind: "none"; thresholdDeg: number; minSunAltitudeDeg: number; at: Date };
export interface HorizontalPosition { time: Date; altitudeDeg: number; azimuthDeg: number }
export interface EquatorialJ2000 { raHours: number; decDeg: number }
```

#### 2. Candidate parameters

**File**: `src/lib/engine/parameters.ts`

**Intent**: Give the PRD's uncalibrated candidates one named home so nothing downstream hardcodes them.

**Contract**: `darknessThresholdDegForBortle(bortle: 1..9): -18 | -15 | -12` (Open Question 7), `ALTITUDE_TOLERANCE_DEG = 1`, `TIME_TOLERANCE_MINUTES = 5` (Open Question 9), `DEFAULT_TRACK_STEP_MINUTES = 10`. Each carries a comment naming its PRD Open Question and the word "candidate".

#### 3. Observing night

**File**: `src/lib/engine/night.ts`

**Intent**: Turn an evening date plus IANA zone into the UTC interval the rest of the engine searches.

**Contract**: `observingNight(date: string, timeZone: string): ObservingNight` — `start` is the instant whose wall clock reads 12:00 on `date` in `timeZone`, `end` the same for the following calendar day (so the 2026-10-24 Warsaw night is 25 h long). Validates `date` against `^\d{4}-\d{2}-\d{2}$` and a real calendar day *before* any `Date.UTC` call (which returns `NaN` silently on garbage) and throws on a malformed date; unknown zones throw because `Intl.DateTimeFormat` raises `RangeError` for them. Also exports `localNoon(date, timeZone): Date` and `addDays(date, n): string`. Uses only `Intl` (see Critical Implementation Details).

#### 4. Sun events and dark window

**File**: `src/lib/engine/sun.ts`

**Intent**: The night's usability skeleton — when the sun sets, when it is dark enough, when it rises.

**Contract**: `sunEvents(site, night): { sunset: Date | null; sunrise: Date | null }` via `SearchRiseSet`; `darkWindow(site, night, thresholdDeg): DarkWindow` per the `SearchAltitude` semantics in Critical Implementation Details; `sunAltitudeDeg(site, time): number`. Observer built once per call from `Site` (elevation default 0). All returns are new objects; no module-level mutable state.

#### 5. Fixture schema, protocol and files

**Files**: `src/lib/engine/fixtures/README.md`, `src/lib/engine/fixtures/stellarium/warsaw-2026-10-10.json`, `src/lib/engine/fixtures/stellarium/warsaw-2026-10-24.json`, `src/lib/engine/fixtures/stellarium/tromso-2026-06-21.json`, `src/lib/engine/fixtures/index.ts`

**Intent**: A single place where hand-read Stellarium values live, with the exact steps to capture them so the reading is repeatable.

**Contract**: Each fixture:

```jsonc
{
  "site": { "name": "Warsaw centre", "latitudeDeg": 52.23, "longitudeDeg": 21.01, "elevationM": 110, "timeZone": "Europe/Warsaw" },
  "night": "2026-10-10",
  "source": { "tool": "Stellarium", "version": "", "capturedBy": "", "capturedAt": "" },
  "sun": { "status": "pending", "sunset": null, "sunrise": null, "darkStart": { "thresholdDeg": -18, "time": null }, "darkEnd": { "thresholdDeg": -18, "time": null } },
  "moon": { "status": "pending", "samples": [ { "time": null, "altitudeDeg": null, "azimuthDeg": null, "illuminatedFraction": null } ] },
  "objects": { "status": "pending", "samples": [ { "id": "M31", "time": null, "altitudeDeg": null, "azimuthDeg": null } ] }
}
```

Times are ISO 8601 **with numeric offset** (e.g. `2026-10-10T17:52+02:00`), read to the minute. Tromsø's `sun.darkStart`/`darkEnd` are expected `null` with `"expectNoDarkness": true`. Section `status` values are `pending | captured | not-applicable`. The `moon` section is required for `warsaw-2026-10-24` (waxing gibbous, above the horizon all night; full moon 2026-10-26) and `tromso-2026-06-21`; for `warsaw-2026-10-10` it is emitted as `"status": "not-applicable", "reason": "new moon 2026-10-10: Moon within degrees of the Sun and below the horizon for the whole dark window"`. The README protocol: set Stellarium's location to the fixture coordinates and elevation exactly (not a city preset), keep atmosphere on and record **apparent** altitude, use the Astronomical Calculations window for rise/set and step time until the Sun's altitude reads the threshold for dark start/end, record Stellarium's version. For moon and object readings: select the body by name (Moon, `M31`, …), read the **apparent** Az./Alt. line and, for the Moon, the illumination percentage, note the displayed time to the minute, and capture at least two Moon instants on 2026-10-24 and three objects per Warsaw night, choosing objects above 20° altitude at the chosen instant. Each section's `status` flips `pending → captured` when filled. `fixtures/index.ts` is test-only code: it statically imports the three JSON files, exports the `Fixture` type as a discriminated union per section (`pending` with null values, `captured` with non-null values, `not-applicable` with a `reason`), and exports a narrowing helper `capturedSections(fixture)` so tests never touch `any` or non-null assertions. No filesystem access exists anywhere under `src/lib/engine/`.

## Phase 3: Moon and object positions

### Overview

Add moon state and separation, object altitude/azimuth tracks, and the best-window primitive; assert them against Stellarium fixtures; prove determinism and the catalogue-wide timing budget.

### Changes Required:

#### 1. Moon

**File**: `src/lib/engine/moon.ts`

**Intent**: Everything the moon-interference score component will need, computed once per sample.

**Contract**: `moonState(site, time): HorizontalPosition & { illuminatedFraction: number; phaseAngleDeg: number }` via `Equator(Body.Moon, …, ofdate=true)` + `Horizon(…, 'normal')` + `Illumination(Body.Moon, time)`; `moonSeparationDeg(time, target: EquatorialJ2000): number` via `AngleBetween` of the Moon's geocentric vector and the target's J2000 unit vector rotated to of-date (topocentric parallax ignored; document the ≤1° error bound); `moonTrack(site, interval, stepMinutes)`.

#### 2. Object positions

**File**: `src/lib/engine/objects.ts`

**Intent**: Where a fixed deep-sky object is at any instant, and when it is best placed during the night.

**Contract**: `objectPosition(site, time, target: EquatorialJ2000): HorizontalPosition` using the J2000→of-date rotation from Critical Implementation Details; `objectTrack(site, interval, target, stepMinutes = DEFAULT_TRACK_STEP_MINUTES): HorizontalPosition[]` sampling inclusive of both ends; `bestWindow(track, minAltitudeDeg): { start: Date; end: Date; peak: HorizontalPosition } | null` returning the longest contiguous run at or above `minAltitudeDeg` (ties → the earlier run) and its highest sample. The window is computed over whatever interval the caller passes; S-02 passes the dark window.

#### 3. Barrel

**File**: `src/lib/engine/index.ts`

**Intent**: One import path for S-02 and later slices.

**Contract**: Re-exports types, parameters, `observingNight`, `sunEvents`, `darkWindow`, `sunAltitudeDeg`, `moonState`, `moonSeparationDeg`, `moonTrack`, `objectPosition`, `objectTrack`, `bestWindow`.

#### 4. Moon and object tests

**Files**: `src/lib/engine/moon.test.ts`, `src/lib/engine/objects.test.ts`

**Intent**: Independent-truth checks plus internal consistency.

**Contract**: Synthetic: `illuminatedFraction` in [0,1] and, for Warsaw 2026-10-24 (waxing gibbous, full moon 2026-10-26), strictly increasing across the night (2026-10-10 is a new-moon night and is never used for moon assertions); separation is symmetric and in [0,180]; for M31 at Warsaw on 2026-10-10 the track's peak altitude is within 1° of `90 − |52.23 − 41.27|` (upper culmination geometry), and M31's azimuth at the transit instant returned by `SearchHourAngle(…, 0)` is within 2° of 180 (the sampled peak is not used for the azimuth check: at 79° altitude azimuth moves about 1° per minute, so a 10-minute grid can sit 5° off); an object with `decDeg = -60` never rises above 0° at Warsaw; `bestWindow` returns `null` when nothing clears `minAltitudeDeg`, and picks the earlier of two equal-length runs. Fixture-driven: for every fixture with `moon.status`/`objects.status === "captured"`, each sample within `ALTITUDE_TOLERANCE_DEG` for altitude and azimuth (azimuth compared circularly) and `illuminatedFraction` within 0.02; pending → `test.todo`.

#### 5. Determinism and budget tests

**File**: `src/lib/engine/determinism.test.ts`

**Intent**: Turn the PRD's determinism NFR and the ranking-time NFR into failing tests rather than intentions.

**Contract**: Running `darkWindow` + `moonTrack` + `objectTrack` for all 110 catalogue objects for Warsaw 2026-10-10 twice yields deep-equal results (Dates compared by `getTime()`); the same full run always logs its measured time and asserts `< 1000 ms` locally and `< 3000 ms` when `process.env.CI` is set (the env read lives in the test file, which the purity guard excludes); the local bound is the position-sampling share of the PRD's "ranking under a second".

## Testing Strategy

### Unit Tests:

- Catalogue: count, uniqueness, overrides (M102 → NGC 5866, M45 → Mel 22), coordinate ranges, type union, normalised constellations, metadata pin.
- Night: 24 h vs 25 h windows across the DST change; invalid zone throws.
- Sun: window inside night, threshold crossings, nested thresholds, Tromsø `none` variant, Stellarium fixtures within 5 min.
- Moon: fraction bounds and monotonicity, separation symmetry, fixtures within 1° / 0.02.
- Objects: culmination geometry, never-rising object, `bestWindow` tie-break and `null`, fixtures within 1°.
- Determinism: deep-equal double run; timing under 1000 ms for the whole catalogue.
- Purity guard: no clock/env/network tokens in `src/lib/engine/`.

### Integration Tests:

- None in this change; the first integration is S-02 consuming the barrel.

### Manual Testing Steps:

1. Follow `src/lib/engine/fixtures/README.md` to set Stellarium to Warsaw (52.23 N, 21.01 E, 110 m) and read sunset, sunrise, −18° dusk and dawn for 2026-10-10 and 2026-10-24 to the minute; repeat for Tromsø 2026-06-21 confirming −18° is never reached.
2. Read moon altitude/azimuth/illumination at two instants on the 2026-10-24 Warsaw night and one for Tromsø (2026-10-10 is a new-moon night, no moon reading); read three object altitudes/azimuths per Warsaw night.
3. Flip each fixture section to `captured`, run `npm test`, confirm green.
4. Compare `bestWindow(M31).peak.time` with Stellarium's transit for 2026-10-10.

## Performance Considerations

The timing test bounds the position-sampling share of the ranking budget: 110 objects × ~85 samples (14 h at 10-minute steps) plus moon and sun searches must finish under 1000 ms locally (3000 ms on a shared CI runner). If it does not, coarsen `DEFAULT_TRACK_STEP_MINUTES` to 15 before optimising code. Bundle size: astronomy-engine is under 120 KB minified, acceptable for the Workers bundle; `messier.json` is ~30 KB.

## Migration Notes

None. New files only, plus one CI step, one `package.json` change and doc edits. Regenerating the catalogue later means bumping `PINNED_SHA`, re-running the script and reviewing the diff.
