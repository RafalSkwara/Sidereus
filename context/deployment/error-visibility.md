# Error visibility: operator runbook

What to look at when something fails in production, and what the owner switches on in the Cloudflare dashboard. Written for someone under stress: the first section is the one to read. Anything not confirmed is marked **unverified**.

## 1. How to read a line

Every failure the app handles leaves one line from `src/lib/observability/log-failure.ts`:

- `sidereus: <step> failed`, at error level: a real fault. Workers Issues records it.
- `sidereus: <step> noted`, at warn level: an expected condition (a refused write, a stale id, a stale session on a write). It is counted, never meant to be an Issue.
- A second argument with `step`, `name`, `code`, `status`. Those fields are for **reading** a line. They carry no message, stack, URL, value or identifier of ours, on purpose.

**Search by message text, never by field.** A two-argument `console.error(message, fields)` is not indexed as fields in Workers Logs (found on production, 2026-10-16: filtering on `step` finds nothing). The step is in the message, so every saved query, alert and count query contains the message text, for example `sidereus: save.log failed`. To see every line the app writes, search `sidereus:`.

In the dashboard: Workers & Pages -> `sidereus` -> Observability -> Logs (path from the Cloudflare docs). The exact name of the text-search or "contains" control is **unverified**: the Workers Logs page of the docs does not describe the query builder.

Retention is 7 days on the Workers Paid plan (Cloudflare docs). Logs cannot be deleted by us.

## 2. First thing to look at

Order from the audit's root causes (`context/audits/observability/2026-10-15_tonight-save-routes-auth-finder-plan.md`):

1. **`forecast.*`**: Open-Meteo or KV. Every user on every site is degraded and the page still answers 200 (audit F1, the worst blind spot). Read `code` on a `forecast.fetch` line: `request` (network or timeout), `http` (with `status`, 429 and 5xx are the provider), `parse` (body not JSON), `schema` (the provider changed its response).
2. **`auth.claims` or `config.supabase`**: an Auth outage or an unconfigured deploy reads as a mass sign-out (RC4, F3, F24). Check Supabase Auth status and the Worker's secrets first.
3. **`save.* failed`**: a save outage. The user sees the neutral server-fault message, not a "could not save" that blames their data (RC1, F4).
4. **Several Supabase steps at once** (`tonight.sites`, `read.*`, `save.*`, `account.plan`): a Supabase outage or an RLS regression. One `code` on all of them points the same way. Check Supabase before the code.
5. **`tonight.build`, `tonight.planets`, `tonight.moon`, `tonight.sky-view`, `tonight.session-plan`, `tonight.sky-events`**: a code fault in the engine or a bad stored time zone. Look at what deployed just before the first line.
6. Everything else in the table below.

The `auth.*` lines carry the error name, the status and, when it is one of auth-js's documented error codes, that code (for example `over_request_rate_limit`). A `code` is logged only from a closed list: a SQLSTATE, a `PGRST` code, the four forecast steps or an auth-js code; anything else is dropped, never logged (impl review F7).

## 4. Stale-id notices versus Issues (D12)

`logFailure` writes at error level, which Workers Issues records. `logNotice` writes at warn level, for conditions that are the user's request or the session and not an outage: a refused write (`42501`), a session fault on a write, a write that matched no row, and the sky-check record's non-server results. The line says `noted`. Docs list "logs an error" among the recorded events and do not list warnings, so a `noted` line should create no Issue. **Unverified on production until 6.5**: the owner makes a deliberate stale-id update and confirms a warn line and no Issue.

## 5. Workers Issues

**Is it on?** In the dashboard open the Issues page for the Worker. If it offers "Enable issues", it is off. The switch lives in `wrangler.jsonc` (`observability.issues.enabled: true`), because a dashboard-only enable is turned off by the next deploy; `src/lib/wrangler-config.test.ts` fails CI if the setting is removed. The built config can be checked with a grep for `issues` in `dist/server/wrangler.json` after `npm run build`. Issues only processes traffic after it was enabled.

**Grouping (confirmed on production, 2026-10-16).** A real `sidereus: forecast.fetch failed` error produced an Issue, and the Issue groups repeated occurrences of the same message. One fixed message per step therefore groups per step. That a second step becomes its own Issue is expected and checked at 6.5.

**Script version (D6).** After PR #187 there is no invocation row (section 6). Open one of our own `sidereus:` console lines in Workers Logs and look in its own metadata for the script version. The docs do not name the field. **Unverified**: the owner confirms it after #187 deploys; the release-identity follow-up (section 9) covers what lies beyond it.

**The automation (the owner creates it; the owner picks the target).** Click path from the Cloudflare docs (read 2026-10-16):

1. Issues page for the Worker.
2. Automations -> Add automation.
3. Pick a trigger and its value: "Occurrence threshold" (runs once when an Issue's count crosses the threshold) or "Recurrence after inactivity" (runs when an Issue returns after the chosen quiet period). A threshold of 1 acts on the first occurrence.
4. Pick or create a destination: a generic webhook (name, HTTPS endpoint, a webhook secret or mTLS), a chat service, an incident-management tool, or a coding agent. The docs do not list the chat and incident fields; the dashboard form does.
5. Enabled on, then Create.

The docs do not document a filter field, so an automation fires for every Issue of the Worker: no per-step filter exists. Limits from the docs: 50 automations per account.

If a logged error does not become an Issue, use a saved Workers Logs query on the message text (section 1) and record the gap as a follow-up. **Unverified**: whether Workers Logs can alert on a saved query. The Workers Logs page of the docs does not say so.

## 6. What the invocation event held (removed by PR #187)

**State as of 2026-10-16:** the table below describes the invocation event as it was until PR #187 deploys (`invocation_logs: false`); after that deploy there is no such row to read, and the checks that remain are the three below the table. Until then, Workers Logs adds one **invocation event** per request (`$cloudflare.$metadata.type = "cf-worker-event"`), enriched by Cloudflare with what it knows about the request. It is not our line and our code cannot redact it. What it holds, and what to do:

| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Request URL path                           | Yes, including opaque entity ids in a path such as a gear page                                                                                                                             | The plan's position (review F6): ids are not coordinates and are not in our lines. Not an owner-confirmed decision; revisit if the owner disagrees                                                          |
| Query string                               | Yes, redacted (`redact_query_string: true` in `wrangler.jsonc`)                                                                                                                            | Yes: the query carries coordinates and redaction is on                                                                                                                                                      |
| Request headers, `cf-ray`, status, outcome | Yes. Which headers exactly is **unverified** (6.6)                                                                                                                                         | Check at 6.6                                                                                                                                                                                                |
| Script version                             | Yes (D6, to confirm)                                                                                                                                                                       | Yes                                                                                                                                                                                                         |
| **`request.cf`**                           | **Yes, in full, found 2026-10-16 (1.9 FAILED):** latitude, longitude, city, postal code, region, region code, metro code, time zone. A visitor's request carries their IP-derived location | **No.** It breaks "no coordinates in any report". It predates this change (`observability.enabled` was already on). The Logs field search does not find these names (not indexed) but the values are stored |

**Fix: applied by PR #187** (`observability.logs: { enabled: true, invocation_logs: false }`, merged 2026-10-16, so it is in this branch's base and goes live with the next deploy of `main`). Confirm after it deploys:

1. A fresh request leaves no `cf-worker-event` row.
2. An Issue is still created for a logged error. Whether the "failed invocation" Issue kind needs the invocation event is undocumented.
3. Whether the console lines of one request still share an invocation or request identifier. D4's correlation (no custom request id; the lines of one request are put together by Workers Logs' own metadata) rests on it. If they no longer do, per-request correlation is lost and the owner decides.

Existing rows expire with the 7-day retention and cannot be deleted by us.

**Traces** (`observability.traces` in `wrangler.jsonc`) are a separate store and #187 does not change them. Cloudflare's span attributes list city-level `geo.*` attributes (locality, region, country, continent, time zone), the autonomous system, the user agent, `url.full` and `url.path`, and KV key names, with no latitude, longitude, postal code or client IP, and no supported redaction. **Owner decision, 2026-10-16: keep traces enabled for now, no follow-up PR.** They carry city, region, country, continent, time zone, the user agent, `url.*` and KV key names **by platform design**, with no supported way to drop them, and they are under GDPR review (#191). Fallback if that review says no: turn traces off, and keep slow-request visibility with a rounded duration field on our own notice line. This change does not touch `traces`.

Our own lines hold none of this (D4): no identifier, user, site, URL, value, coordinate or email.

## 7. The probe, and what it showed

The Version URL probe (an uploaded version with a dead forecast address) did not produce a line or an Issue in Workers Logs, so it was not used as proof; a real production error was found instead (grouping confirmed, `step` field not filterable, both in sections 1 and 5). The probe Worker was skipped and removed. `preview_urls` is now pinned to `false` in `wrangler.jsonc`, so no later Worker version has a public URL. The uploaded probe version stays in the version list with no traffic.

## 8. Client reporting

**Planned, a separate PR (Phases 7-9, a cuttable block with a deadline of 2026-11-04).** Nothing in the browser (the service worker, the React islands) reaches these logs today; the allowlist in `src/lib/observability/silent-catch-guard.test.ts` lists those catches with that reason. When built, client reports arrive as warn-level `sidereus: client.<step> noted` lines, never as Issues, because the endpoint is public. A real burst is then found by a saved Workers Logs query that **counts those lines by message text** (`sidereus: client.`), with a threshold; the same rule as section 1. Whether a query can alert is unverified.
